#### 0. Run an explicit preflight and select a profile

Distinguish testing this routine from completing a repository audit:

- **Routine pilot:** verify access, provenance, credential isolation, dependency readiness, report generation and a small representative workflow. Measure the pilot itself. A static-only pilot is a partial pilot, not evidence that runtime checks work or that the repository is correct.

- **Rotating daily slice:** perform the selected bounded question and applicable gates. The complete audit remains cumulative; inventory and review coverage still account for unchanged files. Not-scheduled methods are neither passed nor failed today.

Before executing repository code, dependency build hooks or repository workflows:

1. Verify the chosen revision's tracked file inventory and bytes. Include the exact lockfile, saved-result files and binary assets needed by checks. For a cached snapshot, compare Git blob identities with the remote manifest; do not equate a folder name with a verified revision. Check and disclose unrelated extra files. If Git metadata is restored, verify original object hashes rather than making a new commit and labeling it as the original revision.

2. Verify that the execution boundary actually prevents repository code from reading connector credentials, authentication files and other secrets. A clean subprocess environment, offline mode, or denied network calls alone do not provide filesystem isolation. Prefer a dedicated environment with no such credentials available, or an enforced filesystem sandbox with a narrow allowlist. Test the boundary with harmless sentinels outside the allowed tree and denied operations; do not print or copy real credential values. Do not substitute a newly written, unverified security wrapper for a working isolation boundary.

3. If this worker lacks a verified execution boundary, block its repository imports, builds, tests and workflows. Continue trusted static parsing, metadata-only lock checks, non-executing hash-verified downloads, research scouting and reading remote evidence. Run metadata-only uv checks on copies of the four manifests and lock with --offline --no-build --no-python-downloads and an explicit actual host interpreter (--python sys.executable or its verified equivalent); do not inherit an absent UV_PYTHON selection. Distinguish a consistent lock, verified downloads, resolved installed versions and actual execution. A verified wheel download alone does not prove an installed/native runtime. Use an inspected, separately authorized existing isolated runner when available, proving that run's filesystem/network/process/child boundary before project imports. Keep credentials and publishing tools outside repository execution. Each host must establish its own boundary. A previously tested command or helper unit suite is not a sandbox certificate. Remote evidence must retain exact source SHA, actual runner checkout, interpreter, commands, job start/completion times and original outcomes; never label it local execution. Obtain materially missing fresh evidence only through available authorized mechanisms; do not duplicate in-flight work or retry a known baseline failure just to obtain green status. A runner or platform block does not stop independent accessible work, and missing required evidence still makes the audit incomplete.

4. Install the exact locked runtime environment inside the verified boundary. If reusing a cache, verify the selected interpreter's resolved dependency graph and installed versions, including environment markers and extras, against the audited lockfile. Pin and hash auditor build dependencies in a separate build environment so they cannot replace the runtime lock's packages. A lockfile or downloaded wheels alone do not prove the installed environment. Resolve mismatches before runtime, performance or reproducibility claims. Give temporary build/test fixtures disk-backed storage inside the isolated writable workspace (for example TMPDIR=/work/tmp, created before use), rather than relying on a small retained /tmp tmpfs across suites. Record disk and enforced memory/CPU/process limits; temporary-storage failure is an environment failure, not proof of a product assertion failure. Do not weaken isolation or increase resource budgets silently to obtain a pass.

5. Establish explicit setup, per-case and total execution budgets before launching long work. A routine pilot should start small; a default of 60 seconds per short case and 10 minutes of execution is a planning limit, not a promise of completing an audit. Record any override and keep setup time separate. The daily plan is 120 minutes total: about 20 for common checks/setup, 70 for the primary field and 30 reserved for independent verification, checkpoint and reporting. Reallocate inside the total without dropping required evidence or the report. The pilot's short-case limits are not the daily allowance; record bounded per-job timeouts and remote compute separately. If the budget tightens, defer in this order: the XL benchmark, second review of low-severity candidates, additional test-quality reading, the second historical replay, then recommendations beyond the top three. Record each deferred item; preserve high-impact verification and the final report.

Record preflight results separately: access, source identity, isolation, dependencies, available platforms, output persistence and selected profile. A failed prerequisite must not be silently converted into a passed check.

Measure the routine at two levels: total elapsed time including setup, and each executed stage's elapsed time, peak memory where measured, scope and outcome. Record tool/model usage only if genuine usage metadata is exposed. Do not infer token cost or claim audit detection accuracy, recall or false-positive rates without independently labeled evaluation cases. Do not infer the full audit's runtime from a static pilot or a CI job's duration.
