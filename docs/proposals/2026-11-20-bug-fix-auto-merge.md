# Proposal: may the daily bug fix merge its own pull requests?

Draft for review, written 2026-11-20, revised 2026-11-21 after ChatGPT's first review 2026-11-22 after the user's addition, ChatGPT's second review and two blind reviews, and 2026-11-24 after ChatGPT's INV-PR70-005 and a third blind review (section 7). **Nothing is decided.** The user picks one of the options below; until then the bug fix never merges and nothing on `main`, in the routine or in the repository settings changes. This file is in a draft pull request so that the ChatGPT open-PR review can check the options before the user picks one.

## 1. The rule today

- The bug-fix skill in the project library (version 15.3 by the project memory's change log; the file carries no version line), first hard limit: "**Never merge.** Do not merge or squash any pull request, push to `main`, approve, enable auto-merge, or close or reopen pull requests."
- The routine's prompt (version 13), constraint 4: "Never merge into main. Never push to main, approve, enable auto-merge, or close or reopen a pull request."
- The user set this constraint on 2026-10-25 ("never merge into main"). Allowing merges reverses it, so it needs the user's explicit yes.
- In practice, merges happen in batches: the user tells a Claude thread to "merge the safe ones in best order" (2026-11-11, 11-14 and 11-18). That thread calls a pull request **safe** when CI is green on every job and ChatGPT's review is clean on the current head. A head pushed after ChatGPT's last review waits for its next pass.
- [GIT_GUIDELINES.md](../../GIT_GUIDELINES.md#pull-requests-and-checks) recommends a protected `main` with required checks. `main` has no branch protection today. CI runs on each push to a pull request and on each push to `main`, but it does not run again when `main` moves under an open pull request.

What the evidence says: the routine's own ladder let about one pull request in five through with a real defect, and the ladder plus ChatGPT let none through. Any merge by the routine must therefore wait for ChatGPT. The user asks for **two** ChatGPT confirmations. Two confirmations therefore take two passes, about two days.

Risks specific to this repository:

1. **Stale CI and a merge race.** Without protection, a squash merge goes through even when `main` moved after the last CI run. The merge call's expected SHA pins the pull request's head, not `main`, so reading `main` once more right before the call cannot close the gap: only a ruleset on `main` that requires the checks and an up-to-date branch does.
2. **TODO.md and README conflicts.** Almost every bug-fix pull request adds REVIEW items. Each merge pushes a conflict onto the other open pull requests, and resolving it resets their CI and their ChatGPT review.
3. **One GitHub account.** ChatGPT, every Claude session and the user all write as `sasasqt`, so a comment's author login proves nothing and a marker can be copied. What GitHub does record server-side is the GitHub App that created a comment (`performed_via_github_app`: OpenAI's `chatgpt-codex-connector`, id 1144995, on every ChatGPT comment; Anthropic's `claude` on every Claude reply), which gate 4 uses. It does not record, in any API these sessions can reach, who edited a comment afterwards; ChatGPT's own run record is not in the repository (the `gpt/repo-audits` branch holds the audit's records, not the review's). A merge by the routine also shows as the user's.
4. **Decisions inside fixes.** Some fixes carry the user's design calls. High-severity fixes change results the most.
5. **Undo.** A bad merge is undone by a revert pull request. That is easy for one squash commit and harder once later merges build on it.

## 3. Options

| | Option | What merges without the user | Effect |
|---|---|---|---|
| A | **Gated auto-merge, no high fixes** (recommended) | at most one bug-fix pull request per run that passes every gate in section 4 | about 2 days from opening to merge while `main` stays still; each merge moves `main`, so the other pull requests then need two fresh passes: about one merge every two days in all, which slows the cap stalls rather than ending them |
| B | Auto-merge mirrors, coverage and typing only | generated mirrors, tests-only and types-only pull requests, under the same gates | coverage and typing keep growing; the cap of five is unchanged, because those never count toward it |
| C | Daily one-tap merge card | nothing; after ChatGPT's pass, the routine posts one card listing the pull requests that pass the gates, and the user's one tap lets a thread merge the first of them | about one merge every two days, as under A, because each merge moves `main` and the next pull request needs two fresh passes, unless the user authorizes a batch on integration heads (section 5); the rule stays as it is |
| D | Keep it manual | nothing | as today |

## 4. Gates (options A and B; option C uses gates 1 to 6 to build its list)

All must hold at merge time, checked by the routine from the pull request body, GitHub state and its own files. If one fails, nothing merges and the run's report says which gate failed and why.

1. **Which pull requests.** The head branch starts with `claude/project-thread-7rf56w-` (the routine's own). Ready for review, not a draft. No `hold` label. Under A: fix pull requests whose `Fixes:` line names only rows the hunt ledger rates low or medium (the routine's rating; ChatGPT's may differ, as on #51), docs-only pull requests, mirrors, coverage and typing. Under B: mirrors, coverage and typing only.
2. **Exclusions.** Any row in the `Fixes:` line rated high. "Checkpoint due" in the title. A `## Held for your decision` section whose question has no answer recorded in `decisions.md`. Any `[not second-reviewed]` mark in the body, or the pull request named in `state.json`'s `not_second_reviewed` (the usage guard skipped reviewer 2, so the signs below were never checked). Any hunk under `.github/`, in `uv.lock`, in a `pyproject.toml` dependency table (coverage floors under `[tool.invest.coverage]` are allowed), or in GIT_GUIDELINES.md, PYTHON_GUIDELINES.md, CI_CD_GUIDELINES.md, DESIGN_BY_CONTRACT.md, RAPID_DEVELOPMENT.md or README.md between `## Development guidelines` and the next `## ` heading, except the mypy and type-rule lines the skill lets a typing pull request change. And three signs that the fix is not settled (the user's rule of 2026-11-22):
   - a **design choice that changes behaviour or results**: a new refusal in place of a warning, a changed default, formula, or format or version constant, or a deliberate difference in the `## Checks` reference comparison between `main` and the branch, unless the body names what decides it: the spec line the fix implements (a doc or TODO item), a `decisions.md` entry, or the user's words in the routine's thread (quoted by the routine, so a record rather than proof). Step 8 adds this list to the body (section 5).
   - an **open question**: an item under "Decisions needed" in the most recent run report that names the pull request, its branch or any ID in its `Fixes:` line.
   - a **disagreement**: an item in `## Review` where reviewer 2's call differed from the run's and the run did not adopt reviewer 2's call (left as it was, or settled by the verifier). Calls about wording, names or the shape of a test that the run adopted stay with reviewer 2.
3. **Own reviews.** The `## Review` section lists the ladder rounds with every finding resolved, and every ChatGPT finding ID (`INV-PR<n>-…`) in the maintained comment has a later reply from the routine or a later commit.
4. **Two ChatGPT confirmations, created through OpenAI's GitHub app, bound to head and target.** Provenance first. GitHub records server-side which GitHub App created a comment, in the REST comment object's `performed_via_github_app` (read with `gh api repos/<owner>/<repo>/issues/comments/<id>`; the GitHub MCP tools drop the field). Every ChatGPT comment on #41, #53, #63 and #70 carries id 1144995, slug `chatgpt-codex-connector`, owner `openai`; every Claude reply carries Anthropic's `claude` app; a comment written in the web interface carries `null`. The maintained comment passes only when that id equals `chatgpt_review_app_id` in `.github/auto-merge.json` on `main` (a missing file or key fails the gate). This proves who created the comment, not who edited it: anyone with write access can edit any comment, every Claude session has `update_issue_comment`, the edit history exists only in GitHub's GraphQL API (`userContentEdits`), and the proxy refuses GraphQL from Claude Code sessions. An edit by another account therefore cannot be detected today, and the gate fails closed: unless `.github/auto-merge.json` also carries `accept_unverified_edits: true`, written by the user, gate 4 fails and the report says why; with that key, every merge report states that the comment's edit history was not checked. Optional hardening, not a prerequisite: a separate GitHub account for the ChatGPT connection, used for nothing else, adds `user.login` as a second check with the same edit limit (on this public repository it needs no access to comment; if the repository went private, a collaborator on a personal-account repository would hold write access, so gate 5's ruleset would have to bind that account too). Then the count. In that one maintained comment: two `invest-pr-review-round:v1` markers with distinct `run` ids, each with `head` equal to the current head and `target` equal to the current `main`, on two different Berlin dates (the user's rule of 2026-11-20: two separate nightly passes; two runs on one date count as one here, a deliberate policy). A marker binds to the first second-level heading after it, which ChatGPT writes as the date, a dash and the conclusion; that conclusion must read "No blocking issues found" (a marker carries no conclusion, so a "Changes needed" round followed by a clean one on the same head is one confirmation, not two). A clean notice (`invest-clean-review:v1`), a status refresh (`invest-pr-status:v1`, whose heading also says "No blocking issues found") and any comment without a round marker count zero. No run registry is readable from the repository: a run id is known when the app-created comment carries it in a round marker followed by its dated heading, and the report quotes it. A new head or a new `main` starts the count again; there is no exemption for a conflict-free merge of `main`, because two reviews of the old `main` say nothing about the new integration. The gate is code with tests (section 5), and the script's verdict, not only its exit code, goes into the report. The tests must fail each of these: two copied markers with matching dated headings in a comment whose creating app is `null` or Anthropic's; a round marker with no second-level heading after it; two markers with the same run id; two rounds on one date; a "Changes needed" round followed by a clean one; one round plus its clean notice; a status refresh counted as a round; two rounds for an earlier head or an earlier `main`; edit history unreadable without `accept_unverified_edits`; a missing `chatgpt_review_app_id`. They must pass one: two rounds in a comment created through app 1144995, distinct run ids, both headings clean, on two Berlin dates, on the exact current head and `main`, with the edit key set or the edit history readable and clean. #63 is the fixture for the real format (head 8821858; rounds on 2026-11-19, 11-21 and 11-22, each with its own run id; the 2026-11-19 heading carries no run id, so pairing by run id would wrongly fail it). Dependencies and limits: (a) two rounds on one head need ChatGPT to review an unchanged head again, which it did on 2026-11-21 (#63, round 2) and not before; docs/GPT_OPENAI_ROUTINES.md and docs/CLAUDE_WORKFLOW.md still describe reuse (hunt row BF-2026-11-20-1), and if reuse returns the pull request waits and the report says so; (b) ChatGPT caps a head at five rounds or comments, so two confirmations fit; (c) the marker names are observed in ChatGPT's comments on #53, #63 and #70, not documented anywhere; (d) the app field and the rulesets of gate 5 are read with `gh api` GET calls, which these sessions' rules allow today only for search, so the routine's prompt must allow these two reads (section 5); (e) edits are the residual limit, decided by the user through `accept_unverified_edits` (open question 1).
5. **Protection on `main`, checked before each merge.** Through GitHub's rulesets API (`gh api repos/<owner>/<repo>/rulesets`, which returns `[]` today; the GitHub MCP tools have no rulesets call): an active ruleset on `main` with a `required_status_checks` rule whose `strict_required_status_checks_policy` is true and whose contexts include every job gate 6 names, and whose `bypass_actors` is empty (field names to confirm against GitHub's API reference when the skill change is written). If it is missing, the routine merges nothing and says so. This is the only guard that closes the gap between the last read of `main` and the merge call: the call's expected SHA pins the head, not `main`.
6. **CI.** Every job is green on the current head, and that head contains the current `main`. Today: `checks (3.11)`, `checks (3.13)`, `wheels` and the three `independent-install` jobs; after #68 merges, `ci-ok` and both `docs` jobs.
7. **Merge.** Squash, with the expected head SHA. At most one merge per run, only after gate 9's advance notice, in step 1e, which runs before step 1 so that a maintenance push cannot change the head after the gates were read.
8. **After the merge.** Wait for `main`'s own CI run. If it fails, open a revert pull request as a held draft, set `merge_paused: true` in `state.json` until the user says to go on, and send the user one phone push.
9. **Advance notice and the veto window.** Checked before the merge, by the same script as gates 1 to 6: the pull request appears in the last posted `announced` list in `state.json` with the same head and the same target (the SHA of `main`), its entry carries the message id of the thread post that named it, and at least `veto_hours` hours have passed since the entry's first announcement. How the list is kept: after each run's report is posted and its phone push has returned, `tools/merge_gates.py --announce` replaces `announced` with exactly the pull requests that report named, taking head and target from the GitHub API, the time from the clock (UTC, ISO 8601) and the post's message id, and keeping the first announcement time of an entry whose pull request, head and target are unchanged. A run cut off before the post leaves the last posted list in place, so the list always matches the last notice the user received. Stopping the option deletes the list (section 6). Who is announced: the script builds the list, too: every pull request that passes gates 1 to 3, 5 and 6 and has at least one of gate 4's two clean rounds on its current head and target. A pull request with two clean rounds but no entry is announced and waits one run; announcing at the first round keeps the time from opening to merge at about two days, because the second round arrives at 21:00 inside the window. A held or draft pull request fails gate 1, so it drops off the list, and after the user releases it, it is announced again and waits. `veto_hours` comes from `.github/auto-merge.json`; the proposed value is 16. The window runs from the announcing report, about 05:30 to 07:00 Berlin on the runs of 2026-11-20 to 11-23, to the next run's step 1e at about 04:10 to 04:30, so the user gets about 21 hours in practice. A floor of 16 hours lets a report as late as about 12:00 Berlin still count, which 20 hours would not (a report after about 08:10 would then delay the merge by one run). The gate fails when there is no list (so the first run after the option starts, or restarts, merges nothing), when the pull request has no entry, when the entry names another head or another target, when it lacks a message id or any other field, when it is younger than `veto_hours`, or when `veto_hours` is missing or not a positive number. The run's report names each merge, the two run ids, the creating app and the rules it read on `main`, says whether the edit history was checked, and lists the announced pull requests with their heads; the routine's one phone push names them. The user stops one by adding the `hold` label or switching it to draft before the next run (both are read as GitHub state, not parsed from text, which is why a comment does not count). The tests must fail each of these: no list; a pull request with two clean rounds missing from the last posted list; an entry for another head; one for another target; one younger than `veto_hours`; one without a message id or with a missing field; `veto_hours` missing, zero, negative or not a number; a pull request held when the last list was built and released since. They must pass one: an unchanged entry past the interval with every other gate holding. And for building the list: one clean round is announced; two clean rounds and no entry are announced; zero rounds, `hold`, draft or red CI are not; an unchanged entry keeps its first time; a changed head gets a new time.

**Two prerequisites are set by the user, and until both exist option A or B merges nothing.** (1) The ruleset on `main` (gate 5): only the user can add a branch ruleset in the repository settings; Claude sessions cannot change settings. GIT_GUIDELINES.md already recommends protected `main` with required checks. (2) `.github/auto-merge.json` on `main`, through a pull request of the user's own (a pull request that touches `.github/` never auto-merges, gate 2), naming the ChatGPT app id, the user's decision on edits and the veto interval (gate 9). `accept_unverified_edits: true` lets gate 4 pass without an edit-history check, which no Claude Code session can run today; `false`, or no key, keeps the gate failing closed, so option A or B merges nothing until GraphQL is reachable. The recommendation is `true`, stated in every merge report: the only accounts that could edit ChatGPT's comment hold write access already, the user can merge directly anyway, every Claude session is bound to write only its own comments, and gate 5's ruleset still enforces CI on whatever merges. A separate ChatGPT account is optional hardening (gate 4).

**Trial.** Fourteen days. Then the routine's report lists what merged, the days from opening to merge and any revert, and the user decides whether to keep the option.

As option A, with gate 1 limited to mirrors, coverage and typing pull requests, and the README and CLAUDE_WORKFLOW sentences naming those three kinds.

- No change to the hard limit or to the prompt's constraint 4.

## 6. How to undo

- **Stop auto-merging:** the user says "stop auto-merge" in the bug fix's thread. The skill goes back to version 15.3 and the prompt to version 13 from the next run, and the `announced` list is deleted from `state.json`, so a later restart starts with a run that merges nothing; a docs pull request restores README and CLAUDE_WORKFLOW.
- **Stop one pull request:** add the `hold` label, or switch it to draft.
- **Undo a merge:** a revert pull request of the squash commit, merged by the user.
- **The ruleset** can stay, since GIT_GUIDELINES.md already recommends it, or be removed in the repository settings.
- **`.github/auto-merge.json`** can stay with `accept_unverified_edits: false`, which alone stops every auto-merge, or be removed.
